GeoID: feature identity independent of storage

Identity architecture within FAO geospatial platform work

GeoID is the feature-identity design within DynaStore’s geospatial work. It separates the identity of a feature from the catalog, collection and backend identifiers used to locate or serve it.

Problem: a location is a fragile identity

Catalog names, storage names and URLs can change as data moves or systems evolve. If these locations are treated as feature identity, a move can look like a new entity to clients and downstream representations.

The design problem is keeping domain identity stable while allowing catalogs, collections and storage drivers to retain their own responsibilities.

Architecture: resolve external references to domain identity

The inspected DynaStore source distinguishes canonical feature IDs from external catalog/collection identifiers and backend document/index names. Write boundaries resolve external references to immutable internal IDs before persistence.

New writable feature identities use UUIDv7. File-backed features derive deterministic UUIDv5 identities scoped by catalog, collection and source feature ID. These are different identity policies for different source capabilities.

Components

Decisions: stable identity is not global ordering or permission

The writable identifier helper describes process-local monotonic behavior and random bits. A UUIDv7 identity is not proof of global transaction ordering, cross-process sequencing or authorization.

Deterministic file identity needs a clear source scope: catalog, collection and source feature ID. A retrospective alternative is deriving identity only from a raw source ID; it is simpler but loses that scoping and can collide across independently named sources.

Outcomes: an identity boundary visible in source

The inspected repository contains identity helpers and item service boundaries supporting this distinction. A published technical article explains the GeoID design.

This case describes source mechanisms and architectural intent. It does not claim all public references are resolvable forever, every data migration is transparent, or identity generation itself enforces access control.

Learning: keep identity, resolution and access distinct

A persistent identifier is useful when the surrounding system can explain resolution, changes and access. Its format alone cannot guarantee those policies.

For further validation I would test source moves, catalog renaming, external-ID reuse and deterministic identity across file reloads, then inspect each authorization boundary independently.

Questions & discussion

Why two UUID strategies?

Writable features need new domain identities. File-backed features can derive identities from a stable scoped source reference. Their guarantees are different and should be tested separately.

Does UUIDv7 establish global write order?

No. The inspected helper’s local monotonic behavior is narrower than a distributed transaction ordering guarantee.

Does knowing a GeoID grant access?

No. Identification and authorization are separate responsibilities. Every route that resolves or serves an entity needs its own access enforcement.
