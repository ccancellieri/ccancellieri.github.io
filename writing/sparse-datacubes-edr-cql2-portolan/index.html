Sparse Irregular Datacubes on Cloud Storage: STAC UAD, EDR CoverageJSON Domains & DuckDB / Portolan SDI

A monolithic Zarr store carries its own coordinate arrays inside .zmetadata. Hundreds of thousands of sparse Cloud-Optimized GeoTIFFs across FAO dekadal or pentadal calendars do not. Here is the zero-custom-endpoint standards architecture that bridges them.

By Carlo Cancellieri · 15 November 2026

Environmental monitoring platforms such as FAO ASIS and CHIRPS rainfall archives routinely expose multi-year time series over non-Gregorian calendars: dekadal (36 periods/year, where the third period of each month runs from day 21 to end-of-month) and pentadal (72 periods/year, where the sixth pentad runs from day 26 to end-of-month). Because 365 mod 10 != 0 and leap years vary February length, an ISO 8601 duration step such as P10D or P5D drifts immediately.

Earlier community discussions around stac-extensions/datacube#36 and #31 explored adding a standalone paginated OGC API – Dimensions surface. Following the architectural convergence in those discussions, that standalone draft was retired in favor of existing and emerging OGC building blocks. While demonstrated here on non-Gregorian agro-climatic calendars, this separation of concerns is fully generic and applies equally to vertical levels, forecast ensembles, administrative hierarchies, or any custom non-spatial dimension. Existing OGC standards already provide every primitive we need — once we distinguish two mathematically different sets:

  • Intensional Calendar Grammar (D): The complete theoretical axis of discrete period definitions (e.g., all 72 nominal pentads of 2021 with exact `[start, end]` boundaries), independent of whether data files exist at a given pixel.
  • Extensional Support (S(AOI, Δt) ⊆ D): The strict subset of populated time slices where one or more raster granules intersect both the user’s spatial Area of Interest and query window.

Why Not Static STAC Summaries or Custom Availability Endpoints?

Static STAC summaries only describe the global union across an entire collection: if pentad 2021-01-P3 has one tile in Southwestern Italy and none in Northeastern Italy, global metadata misleads an analyst zooming into Venice or Milan. Conversely, paginating raw STAC/Features /items over 100,000 granules forces the browser to transfer megabytes of redundant tile polygons just to run DISTINCT(period).

Standard OGC API – Coverages Part 3 defines GET /collections/{collectionId}/scenes for multi-file coverage archives, while OGC API – Features exposes GET /collections/{collectionId}/items for pure vector layers. Pairing either resource with OGC API – Features Part 3 CQL2 (filter=S_INTERSECTS(geometry, POLYGON(...))) and negotiating the RFC 6906 profile parameter defined on application/vnd.cov+json in CoverageJSON 1.0 (OGC 21-069r2 §10) lets the server return a lightweight CoverageJSON "type": "Domain" listing the exact populated time slices — with non-Gregorian values and bounds — in under a kilobyte, while keeping full GeoJSON/STAC Items and pixel extraction strictly separated.

# Raster scene discovery (OGC API - Coverages Part 3 /scenes + CQL2)
curl -H 'Accept: application/vnd.cov+json; profile="http://www.opengis.net/def/profile/covjson/domain"' \
  "https://tellurion-stac-harvest-demo.onrender.com/public/coverages/catalogs/default/collections/fao_chirps_pentadal_2021_italy/scenes?filter=S_INTERSECTS(geometry,POLYGON((13.5%2040.5,14.5%2040.5,14.5%2041.5,13.5%2041.5,13.5%2040.5)))&filter-lang=cql2-text&datetime=2021-01-01T00:00:00Z/2021-01-31T23:59:59Z"

# Pure-vector temporal slice discovery (OGC API - Features /items + profile negotiation)
curl -H 'Accept: application/vnd.cov+json; profile="http://www.opengis.net/def/profile/covjson/domain"' \
  "https://tellurion-stac-harvest-demo.onrender.com/public/features/catalogs/default/collections/dekadal_sparse_granules/items?datetime=2021-01-01T00:00:00Z/2021-01-31T23:59:59Z"

Cloud-Bucket Virtual Cubes: DuckDB File Joins and Portolan SDI

This pattern is equally valuable when there is no heavyweight PostGIS catalog at all. Portolan SDI defines a serverless spatial data infrastructure on object storage: STAC metadata alongside GeoParquet item manifests, Cloud-Optimized GeoTIFFs, PMTiles, and machine-readable AGENTS.md manifests designed for direct querying via DuckDB.

In agricultural analytics, analysts routinely join a GeoParquet manifest of sparse COGs on S3 (items.parquet) with secondary Parquet tables of sub-national crop indicators, watershed masks, or station records inside DuckDB (tellurion-duckdb / OGC API - Joins). Spatiotemporal sparsity is compounded by relational join selectivity: only slices where both a spatial raster intersects the AOI and the joined attribute filter matches exist in the virtual cube.

DuckDB evaluates SELECT DISTINCT period_id, start_datetime, end_datetime via HTTP range reads using Parquet row-group min/max statistics and bounding-box pushdown — touching zero COG pixels — and Tellurion projects that result cleanly onto the wire as a standard CoverageJSON Domain.

Standardization Route: Coverages Part 3, EDR v1.3 & Profile-Negotiated Domain Discovery

Across OGC working groups, the architectural picture is converging cleanly across coverage and vector APIs (see EDR #716, Coverages #218, Coverages #241, and Features #1132):

  • Coverages Part 3 /scenes & Strict Gap Handling: Separating scene metadata on /scenes from pixel extraction on /coverage or EDR /cube (with Prefer: interpolation=none, handling=strict and Content-Interpolation), while supporting a compact Domain-only profile on /scenes.
  • Features /items Profile Negotiation: Using RFC 6906 profile negotiation (application/vnd.cov+json; profile="..." or Accept-Profile, aligned with Features #1031) so Features-only vector deployments can discover populated temporal slices without custom endpoints.
